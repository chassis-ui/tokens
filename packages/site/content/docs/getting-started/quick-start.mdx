## Introduction

This guide takes the shortest way from nothing to tokens in a project, and there are two of them. To use the tokens as they are published, with the brands of the Chassis sites and apps, follow [Use the published tokens](#use-the-published-tokens). To own the tokens, with your brands, themes, apps and platforms, follow [Build your own tokens](#build-your-own-tokens).

## Prerequisites

What you need depends on the way you take.

- **Web**: a project with Sass and a package manager for npm packages.
- **iOS**: an app that targets iOS 13 or later and uses Swift Package Manager.
- **Android**: a module with a minimum SDK of 21 or later.
- **Your own tokens**: Git, Node.js 22 or later and a package manager for npm packages.

## Use the published tokens

The published tokens are the files of `dist/` in [chassis-ui/website-tokens](https://github.com/chassis-ui/website-tokens): the app `docs` for the web, and the app `demo` for iOS and Android, each for the brands `chassis` and `sinefil`. The examples use the brand `chassis`.

### Web

The npm package holds the SCSS files of each brand in `dist/web/docs/<brand>/`. Install it in your project:

```bash
npm install @chassis-ui/website-tokens
```

Use `main.scss` with `@use` and read a token as a variable of the module:

```scss
@use '@chassis-ui/website-tokens/dist/web/docs/chassis/main' as tokens;

.card {
  padding: tokens.$cx-space-context-medium;
}
```

Sass has to find the packages of `node_modules`. With the `sass` command, add `--load-path=node_modules`.

<Callout type="warning">
The published SCSS is written for Chassis CSS. Some variables hold a custom property that Chassis CSS generates: `$cx-color-accordion-item-fg-color` is `var(--default-fg-main)`. Without Chassis CSS, [build your own tokens](#build-your-own-tokens) with a preset that prints values.
</Callout>

The [web guide]([[docsref:/use-in-project/web-applications]]) covers the other files, the themes and the screen sizes.

### iOS

The Swift package holds one library per app and brand, such as `ChassisTokensDemoChassis` for the app `demo` and the brand `chassis`. Add the package `https://github.com/chassis-ui/website-tokens.git` to your app with Swift Package Manager, and add the library of your brand to your target.

Use the constants of the types `ChassisTokens` and `ChassisTokensColor`:

```swift
import ChassisTokensDemoChassis
import UIKit

enum CardStyle {
    static let background: UIColor = ChassisTokensColor.ColorContextDefaultBgMain
    static let padding: CGFloat = ChassisTokens.SpaceContextMedium
}
```

The colors of `ChassisTokensColor` follow the light and dark appearance. The [iOS guide]([[docsref:/use-in-project/ios-applications]]) covers the other types, the screen sizes and the icons.

### Android

The Android library holds the resource tree of one brand. Download `chassis-tokens-demo-chassis-<version>.aar` of the latest release from the [GitHub release](https://github.com/chassis-ui/website-tokens/releases) and copy it to the `libs/` folder of your module.

Add the file to the dependencies in the `build.gradle.kts` of the module:

```kotlin
dependencies {
  implementation(files("libs/chassis-tokens-demo-chassis-<version>.aar"))
}
```

Use the resources in a layout:

```xml
<?xml version="1.0" encoding="utf-8"?>
<LinearLayout
  xmlns:android="http://schemas.android.com/apk/res/android"
  android:layout_width="match_parent"
  android:layout_height="wrap_content"
  android:background="@color/color_context_default_bg_main"
  android:padding="@dimen/space_context_medium" />
```

The library holds the colors of the dark theme in `values-night`, so a color follows the night mode of the device. The [Android guide]([[docsref:/use-in-project/android-applications]]) covers the resource folders, the screen sizes and the icons.

## Build your own tokens

Chassis Tokens is meant to be owned and customized: you make a repository of tokens, change its token sets, name your brands, themes and apps in `chassis.build`, and build it with the `chassis-tokens` command. The token system is built on three core groups, `brand`, `theme` and `app`, and the optional group `screen`; the [introduction]([[docsref:/getting-started/introduction]]) describes them.

### Set up the repository

`chassis-tokens init` writes a repository of tokens into a new folder: a `package.json` with the `chassis.build` block and scripts, a README, a changelog, the workflows of CI and of a release, and a few token sets so that the first build has something to build. `--brand` and `--app` name what it starts with, and `--app` gives each app its platforms:

```bash
npx --package @chassis-ui/tokens chassis-tokens init acme-tokens --brand acme --app site:web mobile:ios,android
cd acme-tokens
git init
npm install
```

`@chassis-ui/tokens` is now a development dependency, and every command runs from the root of the repository. To start from the whole token system of the Chassis sites and apps instead of the few starter tokens, copy `source/` of [chassis-ui/website-tokens](https://github.com/chassis-ui/website-tokens) into the folder before you run `init`, which keeps a `source/` that holds files and writes no starter tokens.

Check the setup with a dry run, which prints the builds and the files of each and writes nothing:

```bash
npx chassis-tokens build --dry-run
```

The plan starts with the web files of the brand:

```text
  • acme_site_light_large
      dist/web/site/acme/: main.scss, string.scss, color-light.scss, number-large.scss
  • acme_site_dark_large
      dist/web/site/acme/: color-dark.scss
```

### Change the tokens

The token sets are the JSON files of `source/`, in Tokens Studio format. Edit them in Figma with Tokens Studio, synced to your repository with the file path `source`, or edit the JSON files directly. A brand is an option of the `brand` group with its own token set, as `brand-acme.json` is for `acme`. The [Tokens Studio guide]([[docsref:/getting-started/tokens-studio]]) describes the token sets and the groups.

Lint the token sets before you build:

```bash
npx chassis-tokens lint-source
```

The lint names the token set and the token of each mistake that the build would accept, such as a token that one screen declares and another does not.

### Configure the build

The build writes only what `chassis.build` lists. The block that `init` wrote, in `package.json`:

```json
"chassis": {
  "build": {
    "brands": ["acme"],
    "themes": ["light", "dark"],
    "screens": ["large", "medium", "small"],
    "apps": {
      "site": ["web"],
      "mobile": ["ios", "android"]
    }
  }
}
```

<CxTable>
| Key | Holds |
| --- | --- |
| `brands` | Options of the `brand` group of `source/$themes.json` |
| `themes` | Options of the `theme` group; the first is the default |
| `apps` | Options of the `app` group, each with its platforms |
| `screens` | Optional: options of the `screen` group; the first is the default |
| `options` | Optional: Style Dictionary options by platform name |
</CxTable>

Replace the names with the options of your groups. Without `screens`, or with `"screens": []`, the build writes one number file for all screens, and `source/$themes.json` must have no `screen` group.

A platform is `web`, `ios`, `android` or a preset: `web-scss`, `web-px` and `web-vw` for a CSS framework other than Chassis CSS, `ios-swiftui` and `android-compose` for SwiftUI and Jetpack Compose. The [Style Dictionary guide]([[docsref:/getting-started/style-dictionary]]) describes every key, platform and preset.

### Build

Build the tokens of the configuration:

```bash
npx chassis-tokens build
```

The build writes the files of every app and brand to `dist/<platform>/<app>/<brand>/`. Filters build a part of the configuration, and you can combine them:

```bash
npx chassis-tokens build --brand acme --platform web
```

After a change to the brands or apps of `chassis.build`, write the manifest of the Swift package again, which has one library for every app and brand with an iOS platform:

```bash
npx chassis-tokens swift-package
```

Review what the change does to the token names and values, compared with the `main` branch, and commit `dist/` with your change. A first build has no `main` to compare with:

```bash
npx chassis-tokens diff
```

Your apps take the files from the folders of `dist/`: the SCSS files of `dist/web/<app>/<brand>/`, the Swift files and `Icons.xcassets` of `dist/ios/<app>/<brand>/`, and `dist/android/<app>/<brand>/res` as a resource folder. The workflow that `init` wrote publishes a tag `v<version>` to npm and attaches the Android libraries to its release, and the repository at that tag is the Swift package. The platform guides describe each.

## Troubleshooting

### Stylesheet not found

Sass stops with `Error: Can't find stylesheet to import.` at the `@use` rule of the tokens. Sass does not search `node_modules` by itself. Add `--load-path=node_modules` to the `sass` command. For a bundler, see the [web guide]([[docsref:/use-in-project/web-applications]]).

### No token sets

The build stops with `No token sets for <brand>_<app>_<theme>_<screen> in source/$themes.json`, with the names of the list it looked for. `chassis.build` lists a brand, theme, app or screen that is not an option of its group in `source/$themes.json`, or it lists no screens while `$themes.json` has a `screen` group. Correct the name in `chassis.build`, or add the option to the group in Tokens Studio.
