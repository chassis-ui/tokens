## Overview

Style Dictionary is a build system that transforms design tokens into platform-specific formats for use in code. It takes the design tokens defined in Tokens Studio and generates CSS, SCSS, JavaScript, Swift, Android XML, and other formats tailored for different platforms and environments.

Chassis Tokens uses Style Dictionary 5 and the Tokens Studio SD Transforms 2 plugin to transform tokens into production-ready code that developers can use across web, iOS, and Android applications.

<Callout type="info" title="Note">
Style Dictionary works hand-in-hand with Tokens Studio. While Tokens Studio manages token definitions and syncs to Figma, Style Dictionary transforms these tokens into code that developers can use in their applications.
</Callout>

### Prerequisites

Before working with Style Dictionary in Chassis Tokens, ensure we have the following:

- **Node.js**: Version 22 or higher required for running the build scripts.
- **pnpm**: Package manager used by Chassis Tokens. Install with `npm install -g pnpm`.
- **Git Repository Access**: Clone or fork the Chassis Tokens repository to access the build configuration.
- **Token Files**: Design tokens must be present in the `tokens/` directory (managed by Tokens Studio).

### How it Works

Style Dictionary follows a transformation pipeline:

1. **Load**: Read the token files of one token-set list
2. **Preprocess**: Align token types and add metadata to the token dictionary
3. **Transform**: Convert token names and the values that are safe to convert before references are resolved
4. **Resolve**: Replace references with the values they point to
5. **Filter**: Select which tokens to include in each output file
6. **Format**: Print one line per token, encoding each resolved value for its platform
7. **Write**: Save generated files to the build directory

Platform encoding (`UIColor(…)`, ARGB colours, `sp` and `dp`, quoting, `em` units and `var(--…)` references) happens in the format step, after references are resolved. It cannot be a Style Dictionary transform: a token such as `rgba({color.base…}, {opacity.level…})` needs the plain values of the tokens it references, not their encoded form.

## Build System

The Style Dictionary build system in Chassis Tokens is configured to handle multi-brand, multi-theme, and multi-platform token generation. The build process transforms tokens based on brand, application, platform, theme, and screen size variations.

Refer to the [Getting Started]([[docsref:/getting-started/quick-start]]) guide for instructions on installing the Chassis Tokens and building token distributions.

### Build Files

The build system is defined in `build/tokens/` directory with the following structure:

- **build.js**: Plans one build per brand, app and token-set list, registers the extensions and runs the builds
- **config/**: Platform-specific settings and file generation logic
- **preprocessor.js**: Token preprocessing before transformation
- **transforms.js**: Custom value transformations (rem, px and vw sizes, and CSS shadows)
- **filters.js**: Which tokens go into which output file
- **formats.js**: Output format definitions (SCSS, Swift, Android XML)
- **templates/**: Custom format templates for each platform; they only print
- **values/**: Value encoders for iOS, Android and web, which run on resolved tokens
- **reference-policy.js**: Which web tokens print a reference and which token it names, shared by both web formats
- **css-var-policy.js**: The `var(--…)` names of the Chassis CSS format
- **scss-var-policy.js**: The values and `$…` names of the SCSS variables format
- **verify.js**: Golden check that compares a fresh build with the committed `dist/`, and each preset with its baseline

### Build Options

Build options are defined in `package.json` under the `chassis` key:

```json
{
  "chassis": {
    "build": {
      "brands": ["chassis", "sinefil"],
      "themes": ["light", "dark"],
      "screens": ["large", "medium", "small"],
      "apps": {
        "docs": ["web"],
        "demo": ["ios", "android"]
      }
    }
  }
}
```

This configuration defines:

- **Brands**: Available brand identities to build
- **Themes**: Color mode variations to generate
- **Screens**: (Optional) Responsive breakpoint sizes. When configured, generates separate number files per screen (e.g., `number-large.scss`). When omitted or empty, generates a single `number.scss` file; `tokens/$themes.json` must then have no screen group
- **Apps**: Applications and their target platforms. A web app can use `web` (Chassis CSS) or one of the [presets for other CSS frameworks](#presets-for-other-css-frameworks)
- **Options**: (Optional) Style Dictionary options by platform name, merged into the options of that platform. The build fails when it names a platform that no app uses:

```json
"options": {
  "android": { "outputReferences": true }
}
```

### Build Command

Generate tokens for every possible brand, theme, and app combination defined in the build options:

```bash
pnpm tokens
```

<Callout type="info">
A full build runs 16 builds, one per brand, app and token-set list, and takes a few seconds. For faster development iterations, use [selective builds](#selective-builds) with CLI arguments to target specific brands, themes, or applications.
</Callout>

### Selective Builds

Use CLI arguments to build specific combinations. All filter options accept space-separated values:

```bash
# Build specific brand
pnpm tokens --brand chassis

# Build specific themes
pnpm tokens --theme light dark

# Build specific application
pnpm tokens --app docs

# Build specific platform
pnpm tokens --platform web ios

# Build specific screens
pnpm tokens --screen large small

# Combine multiple filters
pnpm tokens --brand chassis --theme light dark --app docs
```

**Available options:**

- `--brand <brands...>` — Filter by brand
- `--theme <themes...>` — Filter by theme
- `--app <apps...>` — Filter by app
- `--platform <platforms...>` — Filter by platform
- `--screen <screens...>` — Filter by screen
- `--out <dir>` — Write to another output root instead of `dist`
- `--config <file>` — Read the build configuration from a JSON file instead of `chassis.build` in `package.json`
- `--dry-run` — List the builds and the files each would write, without building
- `--help, -h` — Show help
- `--version, -v` — Show version

### Verify the Output

Check that the committed `dist/` matches a fresh build of `tokens/`:

```bash
pnpm tokens:verify
```

The check builds into `dist-next/` and compares every file with `dist/`, ignoring the timestamp and version lines of the file headers. It also fails when a token name appears twice in one file, and when a reference names nothing the output declares. Add `--platform ios` to build and check one platform only. The release workflow runs this check before publishing to npm.

The presets write nothing into `dist/`. Their reference output is in `build/tokens/test/golden/`:

```bash
pnpm tokens:verify:presets
```

## Platform Support

Chassis Tokens supports multiple platforms with tailored transformations for each.

**Transformation Overview:**

<CxTable>
| Platform | Output | Naming | Unit | Color Format |
|----------|--------|--------|------|--------------|
| Web | SCSS | kebab-case | rem, px or vw; em | hex/rgba |
| iOS | Swift | PascalCase | CGFloat | UIColor |
| Android | XML | snake_case | dp/sp | ARGB hex |
</CxTable>

### Web Platform

The web platform generates SCSS variable files with rem units. The format (`cx/scss-chassis-css`) outputs CSS custom property references for theme-aware values, and resolved values for everything else.

```scss
$cx-border-radius-context-medium: 0.375rem !default;
$cx-color-accordion-item-fg-color: var(--default-fg-main) !default;
$cx-border-radius-accordion-main: var(--border-radius-md) !default;
$cx-space-context-medium: 1rem !default;
```

**Configuration:**

- Base font size: `16px`
- Size transform: `cx/size/rem`
- Prefix: `cx`
- Format: `cx/scss-chassis-css`

### Presets for Other CSS Frameworks

Chassis Tokens is meant to be owned and customized. The `web` platform is set up for Chassis CSS, whose custom properties it references. A team with its own CSS framework needs plain SCSS variables instead. Select one of these platforms for a web app in the build options:

<CxTable>
| Platform | Format | Size transform | Sizes |
|----------|--------|----------------|-------|
| `web` | `cx/scss-chassis-css` | `cx/size/rem` | `1rem` |
| `web-scss` | `cx/scss-variables` | `cx/size/rem` | `1rem` |
| `web-px` | `cx/scss-variables` | `cx/size/px` | `16px` |
| `web-vw` | `cx/scss-variables` | `cx/size/vw` | `1vw` |
</CxTable>

```json
"apps": {
  "docs": ["web-px"]
}
```

All web platforms write the same files to `dist/web/<app>/<brand>/`, with the same names. The presets print resolved values:

```scss
// main.scss (web-px)
$cx-color-accordion-item-fg-color: #161a1b !default;
$cx-border-radius-accordion-main: 6px !default;
$cx-space-accordion-medium-title-padding-y: 12px !default;
```

With the `outputReferences` option they print SCSS variable references instead. See [cx/scss-variables](#cxscss-variables).

The platform files `config/web-scss.js`, `config/web-px.js` and `config/web-vw.js` each call `webConfig({ unit, format })` from `config/web.js`, and can be edited like any other platform file.

### iOS Platform

Generates Swift files with native iOS types. Each file declares its own caseless enum, so all files can be in one target:

```swift
import UIKit

public enum ChassisTokensColorLight {
    public static let ColorContextDefaultFgMain = UIColor(red: 0.086, green: 0.102, blue: 0.106, alpha: 1)
}
```

**Configuration:**

- Naming convention: PascalCase
- Types: `ChassisTokens` in `ChassisTokens.swift`, and `ChassisTokens<File>` in the other files (`ChassisTokensColorLight`, `ChassisTokensNumberLarge`, `ChassisTokensString`)
- Dark mode: with a `light` and a `dark` theme, the build also writes `Color.swift` (`ChassisTokensColor`) after the other builds, where each colour that differs by theme is a `UIColor { $0.userInterfaceStyle == .dark ? … : … }`
- Color output: UIColor with three decimals per channel
- Sizes and numbers: `CGFloat`
- Font families: the first family of the stack only
- Font weights: `UIFont.Weight` constants (`UIFont.Weight.semibold`)
- Icons: the SVG icon tokens also become `Icons.xcassets`, one vector image set per icon, written by the action `cx/ios-icons` in the build of the main file
- Gradients: split into an angle and the colour and position of each stop (`GradientPrimitiveBlackL000Angle`, `…Stop1Color`, `…Stop1Position`)
- Typography parts: a percentage line height becomes points of the token's font size (`125%` of `96` is `120`)
- Imports: UIKit
- References: optional, with `outputReferences` (see [cx/ios-swift-class](#cxios-swift-class))

### SwiftUI and Compose Presets

Two more platforms write native code for apps that do not use UIKit or Android resources. Select them in `chassis.build.apps`, next to or instead of `ios` and `android`:

```json
"apps": { "demo": ["ios-swiftui", "android-compose"] },
"options": { "android-compose": { "packageName": "com.example.tokens" } }
```

<CxTable>
| Platform | Format | Output |
|----------|--------|--------|
| `ios-swiftui` | [cx/swiftui](#cxswiftui) | `dist/ios-swiftui/<app>/<brand>/`, the Swift files of `ios` with `Color` and `Font.Weight` |
| `android-compose` | [cx/compose-object](#cxcompose-object) | `dist/android-compose/<app>/<brand>/`, one Kotlin object per file: `ChassisTokens.kt`, `String.kt`, `ColorLight.kt`, `NumberLarge.kt`, … |
</CxTable>

### Android Platform

Generates Android XML resource files:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<resources>
  <color name="color_context_default_fg_main">#ff161a1b</color>
  <dimen name="space_context_medium">16dp</dimen>
  <dimen name="font_context_lead_font_size">22sp</dimen>
  <item name="opacity_level_10" type="dimen" format="float">0.1</item>
</resources>
```

**Configuration:**

- Naming convention: snake_case
- Size units: `sp` for font sizes, line heights and paragraph spacing, `dp` for other sizes
- Color format: ARGB hex (`#aarrggbb`)
- Opacity and letter spacing: float resources (`<item type="dimen" format="float">`), because Android integer resources reject fractions
- Typography parts: a percentage line height becomes `sp` of the token's font size (`125%` of `96` is `120sp`), and letter spacing is in ems of the font size (`-0.5px` at `96` is `-0.0052`)
- Strings: escaped for Android, so SVG icons and quotes stay text
- Font weights: `integer` resources from 100 to 900 (`600`)
- Icons: the SVG icon tokens also become vector drawables in `res/drawable/`, converted with `svg2vectordrawable` by the action `cx/android-icons`
- Resource tree: `res/values` (strings, base colours, the first theme's colours, the default screen's numbers), `res/values-night` (dark colours) and a `res/values-<qualifier>` per other screen, next to the flat files. The folders of the screens are set with `options.android.screens`, by default `{ "small": "", "medium": "sw600dp", "large": "sw840dp" }`
- Gradients: split into an angle and the colour and position of each stop (`gradient_primitive_black_l_000_angle`, `…_stop_1_color`, `…_stop_1_position`)
- References: optional, with `outputReferences` (see [cx/android-resources](#cxandroid-resources))

## Output Files

Build system generates different file types based on token categories to optimize loading and usage. Generated files are placed in the `dist/` directory organized by platform, application, and brand:

```
dist/
├── web/
│   └── docs/
│       └── chassis/
│           ├── main.scss              (base tokens)
│           ├── string.scss            (string tokens)
│           ├── color-light.scss       (light theme colors)
│           ├── color-dark.scss        (dark theme colors)
│           ├── number-large.scss      (when screens configured)
│           ├── number-medium.scss     (when screens configured)
│           ├── number-small.scss      (when screens configured)
│           └── number.scss            (when screens omitted/empty)
├── ios/
│   └── demo/
│       └── chassis/
│           ├── ChassisTokens.swift
│           ├── Color.swift            (light and dark colours in one)
│           ├── String.swift
│           └── ...
└── android/
    └── demo/
        └── chassis/
            ├── main.xml
            ├── string.xml
            ├── ...
            └── res/                   (resource tree: values, values-night, values-sw…dp)
```

<Callout type="info">
Number token files are generated based on the `screens` configuration:
- **With screens**: Separate files per breakpoint (`number-large.scss`, `number-medium.scss`, etc.)
- **Without screens**: Single file for all number tokens (`number.scss`)
</Callout>

Colour files use the token sets of their theme, and number files the token sets of their screen. The main and string files use the token sets of the first theme and the first screen in the build options.

### Main File

Contains all tokens except theme-level color tokens:

```scss
// main.scss
$cx-color-base-context-light-default-fg-main: #161a1b !default;
$cx-color-base-context-dark-default-fg-main: #e9eced !default;
$cx-color-accordion-item-fg-color: var(--default-fg-main) !default;
$cx-space-context-medium: 1rem !default;
$cx-typography-font-family-text: Inter, system-ui, -apple-system, Helvetica, Arial, sans-serif !default;
$cx-font-context-lead: ("font-family": var(--font-family-text), "font-weight": var(--font-weight-text-normal), ...) !default;
$cx-shadow-context-small: 0rem 0.125rem 0.5rem -0.125rem rgba(0, 0, 0, 0.1), 0rem 0.0625rem 0.25rem -0.0625rem rgba(0, 0, 0, 0.1) !default;
```

**Includes:**

- Base color tokens (`color.base.*`) and component color tokens
- All dimension or number tokens (size, space, opacity, etc.)
- Base typography tokens
- Composite typography tokens (font.\*) as Sass maps
- Shadow tokens
- Gradient tokens
- String tokens, such as font families and assets

### String Files

Contains only string-type tokens:

```scss
// string.scss
$cx-typography-font-family-text: Inter, system-ui, -apple-system, Helvetica, Arial, sans-serif !default;
$cx-typography-font-family-display: 'Archivo Narrow', Georgia, 'Times New Roman', Times, serif !default;
```

### Color Files

Separate files for each color theme to enable efficient theme switching:

```scss
// color-light.scss
$cx-color-context-default-fg-main: #161a1b !default;
$cx-color-accordion-item-fg-color: var(--default-fg-main) !default;
$cx-gradient-primitive-black-l-000: linear-gradient(0deg, rgba(0, 0, 0, 0) 0%, #000000 100%) !default;
```

<Callout type="info">
Loading theme-specific color files separately allows dynamic theme switching without loading all color variations upfront.
</Callout>

### Number Files

Contains numeric token types with units if applicable:

```scss
// number-large.scss
$cx-size-button-medium-main: 2.5rem !default;
$cx-space-context-medium: 1rem !default;
$cx-opacity-level-10: 0.1 !default;
$cx-typography-line-height-text-medium: 1.5em !default;
```

## Transforms

Transforms modify token values during the build process. Chassis Tokens use its custom transforms along with some built-in transforms from Style Dictionary and Tokens Studio SD Transforms plugin. Transforms run before references are resolved, so they only do what is safe at that point; platform encoding happens later, in the formats.

Built-in transforms from Style Dictionary and Tokens Studio SD Transforms plugin:

- **name/kebab**: Converts token names to kebab-case (`size-button-medium`)
- **name/pascal**: Converts token names to PascalCase (`SizeButtonMedium`)
- **name/snake**: Converts token names to snake_case (`size_button_medium`)
- **ts/resolveMath**: Resolves mathematical expressions in token values
- **ts/color/modifiers**: Applies color modification extensions from Tokens Studio
- **ts/color/css/hexrgba**: Converts colors to CSS hex or rgba format
- **ts/typography/fontWeight**: Maps font weight names to numeric values (web; the iOS and Android encoders use the same map)

Chassis-specific transforms defined in `transforms.js`, used by the web platform:

### cx/size/rem

Converts size values to rem units, without rounding:

```javascript
// Input:  24 (with basePxFontSize: 16)
// Output: 1.5rem
```

### cx/size/px

Gives size values the unit px, for the `web-px` preset:

```javascript
// Input:  24
// Output: 24px
```

### cx/size/vw

Converts size values to vw units, without rounding, for the `web-vw` preset. `basePxFontSize` pixels are `1vw`:

```javascript
// Input:  24 (with basePxFontSize: 16)
// Output: 1.5vw
```

### cx/shadow/web

Converts shadow tokens into CSS box-shadow format:

```javascript
// Input:  { offsetX: '0rem', offsetY: '0.125rem', blur: '0.25rem', spread: '0rem', color: 'rgba(0, 0, 0, 0.1)', type: 'innerShadow' }
// Output: '0rem 0.125rem 0.25rem 0rem rgba(0, 0, 0, 0.1) inset'
```

<Callout type="info">
All custom transforms are applied conditionally based on token type and platform configuration to ensure correct output.
</Callout>

## Filters

Filters determine which tokens are included in output files. Chassis Tokens uses custom filters to organize tokens by category.

### cx/allTokens

Used for the main file. Includes all tokens except theme-level colors:

```javascript
// Excludes: color.primitive.*, color.context.*, color.utility.*
// Includes: Other colors, fonts, gradients, numbers, shadows, sizes, strings
```

### cx/themeTokens

Used for the color files. Only theme-level color tokens:

```javascript
// Includes: color.primitive.*, color.context.*, component colors, gradients
// Excludes: color.base.*, color.utility.*
```

### cx/numberTokens

Used for the number files. Number and size tokens:

```javascript
// Includes: duration, letterSpacing, number, opacity, dimension, fontSize, lineHeight, paragraphSpacing
```

### cx/stringTokens

Used for the string files. Only string-type tokens:

```javascript
// Includes: asset, content, fontFamily, fontStyle, fontWeight, string, text, textCase, textDecoration, type
```

Tokens typed `boolean` or `other` are not written to any file.

## Formats

Formats define the output structure for each platform. Chassis Tokens provides custom format templates. The templates only print: each value comes from the encoders in `build/tokens/values/` and, on the web, from the reference policies (`reference-policy.js`, with `css-var-policy.js` or `scss-var-policy.js`).

### cx/scss-chassis-css

Generates SCSS variable files that use CSS custom property references (`var(--…)`) for theme-aware values specific to **Chassis CSS**.

```scss
$cx-color-accordion-item-fg-color: var(--default-fg-main) !default;
$cx-shadow-alert-main: var(--box-shadow-lg) !default;
$cx-font-context-lead: ("font-family": var(--font-family-text), "font-weight": var(--font-weight-text-normal), "font-size": var(--font-size-text-xl), "line-height": var(--line-height-text-xl), ...) !default;
```

**Features:**

- File header with copyright and license
- CSS custom property references for colors, spacing, opacity, shadows, border radius and border width
- Enables runtime theme switching without recompilation
- Composite typography tokens output as Sass maps with `var()` references
- Line heights in `em`, relative to the font size at the same path, and letter spacing in `em`

A token prints a custom property when its value is a single reference to a token that Chassis CSS exposes as one, such as `color.context.*`, `space.context.*`, `opacity.level.*` or `shadow.context.*`. Scale names are shortened to match Chassis CSS (`medium` becomes `md`, `xlarge` becomes `xl`). Any other token prints its resolved value.

<Callout type="info">
CSS custom property references enable runtime theme switching and value inheritance without requiring recompilation of stylesheets.
</Callout>

<Callout type="info">
Composite font tokens (starting with `font.*`) are transformed into Sass maps, making it easier to access and apply typography styles as a complete set rather than individual properties. This enables more maintainable and reusable typography mixins.
</Callout>

### cx/scss-variables

Generates SCSS variable files for CSS frameworks other than Chassis CSS. The `web-scss`, `web-px` and `web-vw` presets use it. It has two modes, set with the `outputReferences` option.

Without `outputReferences` (default), every value is resolved:

```scss
$cx-color-accordion-item-fg-color: #161a1b !default;
$cx-border-radius-accordion-main: 6px !default;
$cx-font-context-lead: ("font-family": "Inter, system-ui, -apple-system, Helvetica, Arial, sans-serif", "font-weight": 400, "font-size": 22px, "line-height": 1.455em, "font-style": normal, "letter-spacing": 0em, "margin-bottom": 0px, "text-transform": none, "text-decoration": none) !default;
```

With `outputReferences`, a token prints the SCSS variable of the token it references, where the Chassis CSS format prints a custom property. Shadows are the exception: they print their value. Typography maps name the variables of their family, weight, style, size and line height:

```json
"apps": { "docs": ["web-px"] },
"options": { "web-px": { "outputReferences": true } }
```

```scss
$cx-color-accordion-item-fg-color: $cx-color-context-default-fg-main !default;
$cx-border-radius-accordion-main: $cx-border-radius-context-medium !default;
$cx-font-context-lead: ("font-family": $cx-typography-font-family-text, "font-weight": $cx-typography-font-weight-text-normal-weight, "font-size": $cx-typography-font-size-text-xlarge, "line-height": $cx-typography-line-height-text-xlarge, "font-style": $cx-typography-font-weight-text-normal-style, ...) !default;
```

**Features:**

- File header with copyright and license
- Resolved values, or SCSS variable references with `outputReferences`
- Composite typography tokens output as Sass maps
- Line heights in `em`, relative to the font size, and letter spacing in `em`, in every unit

<Callout type="warning">
With `outputReferences`, load a colour file (`color-light.scss` or `color-dark.scss`) before `main.scss`: the colour tokens of `main.scss` reference variables that the colour files declare. The other files use only variables they declare themselves. The build fails when a reference would name a variable that no file declares.
</Callout>

### cx/ios-swift-class

Generates a Swift type with static properties:

```swift
import UIKit

public enum ChassisTokens {
    public static let ColorButtonPrimaryBgIdle = UIColor(red: 0.000, green: 0.643, blue: 0.800, alpha: 1)
    public static let SizeButtonMediumMain = CGFloat(40)
    public static let TypographyFontWeightTextStrongWeight = UIFont.Weight.semibold
}
```

**Features:**

- The type is set per file with the `className` and `objectType` options; the iOS config gives each file its own enum. With `objectType: 'class'` the constants are marked `@objc`
- PascalCase property names
- Native iOS types (UIColor, CGFloat)
- Proper import statements
- Public accessibility
- Typography and shadow tokens expanded into one property per part (`FontContextLeadFontSize`)
- Optional references to other constants of the type, with `outputReferences`

With `outputReferences`, a token whose value references another token of the same file names that constant:

```json
"options": { "ios": { "outputReferences": true } }
```

```swift
public static let SpaceContextMedium = SizeUnit16
public static let FontContextJumboFontFamily = TypographyFontFamilyText
public static let BgBlurDefaultColor = UIColor(red: 0.718, green: 0.753, blue: 0.761, alpha: 0.5)
```

The rule is the one of [cx/android-resources](#cxandroid-resources): a token names a constant only when that constant has the same Swift type and value. `BgBlurDefaultColor` is `rgba({color.primitive.neutral.30}, {opacity.context.fg-subtle})`, so it prints its value, because `ColorPrimitiveNeutral30` has no alpha. Base colours and sizes computed with math also print their values. A constant never names one of another file, so a component colour of `ChassisTokens.swift` prints its value where the colour file names a context colour.

### cx/swiftui

Generates the files of the iOS platform with SwiftUI values, for the `ios-swiftui` preset. Colours are `Color`, font weights `Font.Weight`, and every other value is the one of `cx/ios-swift-class`:

```swift
import SwiftUI

public enum ChassisTokensColorLight {
    public static let ColorContextDefaultBgMain = Color(red: 1.000, green: 1.000, blue: 1.000, opacity: 1)
}
```

It supports `outputReferences` with the rule of `cx/ios-swift-class`. The preset writes no `Color.swift`; for colours that follow the appearance, use the UIKit `ChassisTokensColor` through `Color(uiColor:)`.

### cx/compose-object

Generates one Kotlin object per file for Jetpack Compose, for the `android-compose` preset. The values are the ones of `cx/android-resources`, in Kotlin:

```kotlin
package chassis.tokens

object ChassisTokensNumberLarge {
    val spaceContextMedium get() = 16.dp
    val fontContextLeadFontSize get() = 22.sp
    val fontContextJumboLetterSpacing get() = (-0.0052).em
    val opacityLevel40 get() = 0.4f
}
```

Colours are `Color(0xAARRGGBB)`, font weights `FontWeight(600)`, and strings Kotlin literals. Every property is a getter: with `outputReferences` a property may name one declared later in the file, which a stored property cannot. The package is `chassis.tokens`, or `packageName` in `options["android-compose"]`.

### cx/android-resources

Generates Android XML resource files:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<resources>
  <color name="color_button_primary_bg_idle">#ff00a4cc</color>
  <dimen name="size_button_medium_main">40dp</dimen>
  <string name="typography_font_family_text">Inter</string>
</resources>
```

**Features:**

- snake_case resource names
- Proper XML structure
- Type-specific resource tags (`color`, `dimen`, float `item`, `integer`, `string`)
- Android units (dp, sp)
- Typography and shadow tokens expanded into one resource per part
- Optional references to other resources, with `outputReferences`

With `outputReferences`, a token whose value references another token of the same file prints a reference to that resource:

```json
"options": { "android": { "outputReferences": true } }
```

```xml
<dimen name="space_context_medium">@dimen/size_unit_16</dimen>
<string name="font_context_jumbo_font_family">@string/typography_font_family_text</string>
<dimen name="font_context_jumbo_font_size">96sp</dimen>
```

A token prints its value when a reference would not compile or would change the value: when the referenced resource is another element, or encodes to another value (`font_context_jumbo_font_size` is `96sp`, its reference `size_unit_96` is `96dp`). Base colours and sizes computed with math also print their values.

## Preprocessor

The preprocessor runs before transforms and filters, allowing global modifications to the token dictionary.

### cx/global

Located in `preprocessor.js`, this custom preprocessor:

- Aligns Tokens Studio types with Style Dictionary types, using `alignTypes` from Tokens Studio SD Transforms (for example `fontSizes` to `fontSize`, and shadow `x`/`y` to `offsetX`/`offsetY`)
- Types letter spacing tokens as numbers
- Splits every font weight token into a weight and a style (`Light Italic` becomes `Light` and `italic`)
- Stores the font weight path of composite typography tokens, for the web `var(--…)` names
- Numbers the tokens in source order, so that expanded typography and shadow tokens are printed where their source token is

```javascript
StyleDictionary.registerPreprocessor({
  name: 'cx/global',
  preprocessor: (dictionary) => cxPrep(dictionary)
})
```

## Advanced Configuration

### Custom Token Types

Define how Style Dictionary handles custom token types:

```javascript
expand: {
  typesMap: {
    typography: {
      lineHeight: 'dimension',
      paragraphSpacing: 'dimension',
      letterSpacing: 'number'
    }
  }
}
```

This ensures composite typography tokens are properly expanded and transformed on iOS and Android.

### Transform Lists

Each platform configuration lists its transforms explicitly instead of using a transform group:

```javascript
// config/web.js
const transforms = [
  'name/kebab',
  'ts/resolveMath',
  'ts/color/modifiers',
  'ts/color/css/hexrgba',
  'ts/typography/fontWeight',
  'cx/shadow/web'
]

// The size transform of the unit is added last: cx/size/rem, cx/size/px or cx/size/vw
export function webConfig({ unit = 'rem', format = 'cx/scss-chassis-css' } = {}) {
  // ...
  transforms: [...transforms, `cx/size/${unit}`]
}
```

StyleDictionary.registerFileHeader({

## Theme Permutations

Style Dictionary processes theme combinations using the Tokens Studio SD Transforms `permutateThemes` function:

```javascript
const $themes = JSON.parse(await readFile('tokens/$themes.json'))
const sets = permutateThemes($themes, { separator: '_' })
```

This creates one token-set list per brand, app, theme and screen, such as:

- `chassis_docs_light_large`
- `chassis_docs_dark_large`
- `chassis_demo_light_medium`
- `sinefil_demo_light_small`

The build creates one Style Dictionary instance per token-set list it needs, with one platform per target platform of the app. For example, `chassis_demo_light_large` writes the main, string, light color and large number files for both iOS and Android. A full build uses 16 token-set lists.

## Troubleshooting

Common issues and solutions when working with Style Dictionary.

### Build Errors

**Problem**: "Some token references could not be found"

**Solutions:**

- Verify token files exist in `tokens/` directory
- Check `$themes.json` configuration for correct token set references
- Ensure theme option has correct token sets enabled
- Validate JSON syntax in token files

The build stops on any broken reference instead of writing a file with unresolved values.

**Problem**: "No token sets for … in tokens/$themes.json"

**Solutions:**

- Check that every brand, app, theme and screen in the build options has a matching theme in `$themes.json`
- Check the spelling of the names in `package.json`

**Problem**: Build completes but files are empty

**Solutions:**

- Check filter configuration - tokens may be filtered out
- Verify token types match filter criteria
- Review preprocessor logic for token modifications

**Problem**: `pnpm tokens:verify` fails

**Solutions:**

- If you changed tokens, run `pnpm tokens` and commit the updated `dist/`
- If you changed the build scripts and did not mean to change the output, the report lists the first differing lines of each file

### Transform Issues

**Problem**: Size values not converting to correct units

**Solutions:**

- Check platform configuration specifies correct transforms
- Verify `basePxFontSize` is set for the rem and vw transforms
- Ensure token type matches transform filter

**Problem**: Colors not formatted correctly

**Solutions:**

- Verify `ts/color/modifiers` transform is registered
- Check color tokens have valid hex or rgba values
- Review platform-specific color format requirements

### Output Issues

**Problem**: Generated files in wrong directory

**Solutions:**

- Check `buildPath` in platform configuration
- Verify brand and app names match directory structure
- Review `config/` file path generation logic

**Problem**: Missing tokens in output

**Solutions:**

- Verify tokens pass the filter for that file
- Check token set is enabled in theme configuration
- Review file generation logic in `config/`

### Platform-Specific Issues

**iOS:**

- Ensure UIKit import is included
- Verify PascalCase naming convention
- Check CGFloat types for numeric values

**Android:**

- Validate XML structure
- Ensure snake_case naming
- Check dp/sp units for dimensions

## Best Practices

Guidelines for working effectively with Style Dictionary in Chassis Tokens.

### Token Organization

**Separate concerns:**

- Keep base tokens platform-agnostic
- Use platform-specific transforms for output
- Organize tokens by component or feature

**Use semantic naming:**

```scss
// ✅ Good - semantic meaning
$cx-color-button-primary-bg-default

// ❌ Bad - implementation detail
$cx-blue-500
```

### Build Optimization

**Build only what's needed:**

```bash
# Instead of building all combinations
pnpm tokens

# Build specific combinations
pnpm tokens --brand chassis --theme light
```

**Preview before building:**

```bash
pnpm tokens --dry-run
```

### Version Control

**Commit built files strategically:**

Option 1: Commit dist files for direct consumption

- Pros: Consumers don't need to build
- Cons: Larger repository size

Option 2: Build during publish/deploy

- Pros: Smaller repository
- Cons: Requires build step in CI/CD

Chassis Tokens commits `dist/` and runs `pnpm tokens:verify` before publishing, so the published files always match the tokens.

**Document build requirements:**

- Specify Node.js version
- Document npm scripts
- Include build instructions in README

### Testing

**Validate output:**

```bash
# Run tests
pnpm tokens:test

# Check dist/ against a fresh build
pnpm tokens:verify

# Lint the build scripts
pnpm tokens:lint
```

**Test platform output:**

- Import generated files in target projects
- Verify values match design specifications
- Test theme switching functionality

### Custom Extensions

**When to create custom transforms:**

- Platform requires specific format
- Need specialized value conversion that does not depend on referenced values
- Implementing design system conventions

**When to create custom filters:**

- Grouping tokens by feature
- Platform-specific token subsets
- Performance optimization

**When to create custom formats:**

- New platform not supported by default
- Specific file structure required
- Integration with existing systems
